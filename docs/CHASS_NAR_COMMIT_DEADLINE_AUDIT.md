# NAR SQLite COMMIT deadline characterization v1

Research only. Production Activation NO-GO. This patch adds boundary
characterization tests and this document. It does not fix or certify the
strict durable-commit deadline. No runtime, store, Freeze or rule change.

## Confirmed local observations

Six new tests extend the real file-backed SQLite integration suite. They use
the existing persistent Python sqlite3 connections and injected application
clocks. The COMMIT wrapper controls when the real SQLite statement executes
or when its successful acknowledgement reaches the caller. No live NAR data,
production D1 or trusted external clock is used. These are deterministic
synthetic timing experiments, not measurements of production latency.

| Experiment | Current capture | Saved row | Reopened read |
| --- | --- | --- | --- |
| Before executing COMMIT, advance clock to acquisition + 60,001 ms | CREATED | Present | PRESERVED, identical bytes/hash |
| Before executing COMMIT, advance clock to exact post time (age 60,000 ms) | CREATED | Present | PRESERVED, identical bytes/hash |
| SQLite responds within window, driver returns after 60,001 ms | CREATED | Present | Not tested in this case |
| SQLite commits, driver then throws instead of acknowledging | REJECTED / CAPTURE_FAILED | Present | PRESERVED, identical bytes/hash |
| Driver throws before executing SQLite COMMIT | REJECTED | Absent after rollback | Later fresh capture CREATED |
| Clock becomes non-finite or reverses after SQLite COMMIT | CREATED | Present | Not tested in this case |

Freshness permits age exactly 60,000 ms; post time is exclusive. The post-time
test deliberately separates these two boundaries. Its source header uses
12:01 JST and the synthetic acquisition is 12:00 JST, with matching source
seals regenerated by the fixture. It does not represent an official race time.

The first two experiments demonstrate that pre-COMMIT checks cannot enforce
the completion window through an asynchronously injected driver. They do not
prove the precise physical durability instant. The delayed-acknowledgement
experiment separately demonstrates why caller return time and the database's
actual durable commit time must not be treated as interchangeable.

After a lost acknowledgement, the adapter attempts ROLLBACK but the transaction
has already committed; SQLite rejects that rollback. Capture reports failure,
yet the durable row remains. Therefore capture failure alone cannot establish
that nothing was saved. A retry preserves the existing first row, as designed.

Reopened-read assertions use only SELECT, perform no acquisition, and compare
the original stored JSON and hash. No UPDATE, DELETE, time adjustment, repair
or replacement is introduced. Existing PRESERVED means the saved bundle passes
its content/source semantics; it does not certify actual commit completion.

## Interpretation and required next contract

All six tests expect the current behavior. A green result confirms reproduction
of the timing gap; it is not a strict-deadline quality PASS. The old ten tests
continue to establish their narrower persistence and pre-COMMIT claims.

Adding a clock check after COMMIT can detect a late acknowledgement but cannot
undo the commit. Deleting or rewriting that first row would violate immutable
first-version research storage. Nor does a successful application-side return
authenticate official data or trusted wall time.

A future research contract should separate durable content preservation from
eligibility for formal EARLY adoption. It needs independent, persisted timing
evidence bound to the original bundle hash, an explicit unknown/late/failed
acknowledgement state, and a restart admission gate that withholds adoption when
evidence is absent or uncertain. Receipt persistence itself can fail, so a
missing receipt must remain unknown rather than be inferred from sealedAt.
No such receipt, eligibility gate or trusted database deadline is implemented
here. This is a proposed integration requirement, not approved formal logic.

Strict actual commit-completion certification requires a driver/storage timing
contract stronger than the current asynchronous exec/first/run interface.
Whether production D1 can satisfy that stronger contract is unverified. Do not
change the requirement to seal time or statement-start time without explicit
policy review. Formal rule certification and Production Activation remain HOLD
and NO-GO respectively.
